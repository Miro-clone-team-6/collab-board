# Структура backend

## Модули

Код одной области ответственности размещается в `apps/api/src/modules/<name>/`.
Файлы лежат рядом, без обязательных вложенных слоёв.

Пример разделения ответственности будущего модуля досок на четыре слоя:

```text
modules/boards/                         Файлы внутри одного модуля
  boards.controller.ts, board.dto.ts    HTTP: запросы и ответы
                  ↓
  boards.service.ts                     Сценарии: создать, переименовать доску
                  ↓
  board.ts                              Бизнес-логика: допустимые изменения доски

  boards.repository.ts                  Хранение: Prisma-запросы к БД
```

Сервис использует бизнес-логику и репозиторий; бизнес-логика не зависит от
HTTP и Prisma. `boards.module.ts` связывает зависимости.
Отдельный `board.ts` нужен при появлении самостоятельной бизнес-логики;
для простого CRUD достаточно сервиса. Схема показывает роли, а не обязательный набор файлов.

- `*.module.ts` — подключает модули, регистрирует контроллеры и зависимости.
- `*.controller.ts` — принимает HTTP-запрос, вызывает сценарий и задаёт HTTP-ответ.
- `*.dto.ts` — описывает данные на границе HTTP на основе общей Zod-схемы.
- `*.service.ts` — выполняет сценарии и бизнес-логику.
- `*.repository.ts` — скрывает Prisma-запросы и типы хранения от остального модуля.

Provider — объект, который создаёт и передаёт Nest: сервис, репозиторий или
конфигурация. Зависимости передаются через конструктор. В `@Module` поле `imports`
подключает модули, `controllers` регистрирует контроллеры, `providers` — зависимости,
`exports` открывает зависимости другим модулям.

В бизнес-модулях путь запроса: контроллер → сервис → репозиторий → БД.
Бизнес-логика не размещается в контроллерах и DTO.
Use case — отдельный класс одного сценария; выделяется, когда это требуется логике.
Репозитории, use case и интерфейсы заранее не создаются.

Текущий пример — `health`: контроллер → сервис → `PrismaService` → `SELECT 1`.
Это техническая проверка подключения, без бизнес-репозитория.
`UsersModule` пока заглушка без маршрутов и логики.

## Общий код API

Пути относительно `apps/api/`:

- `src/main.ts` — создание приложения и запуск HTTP-сервера.
- `src/configure-app.ts` — общие настройки HTTP: префикс `/api/v1`, защитные заголовки, подключение и освобождение ресурсов приложения.
- `src/app.module.ts` — подключение модулей, конфигурации и глобального фильтра ошибок.
- `src/config/` — загрузка и проверка настроек.
- `src/prisma/` — подключение к БД.
- `src/errors/` — ошибки приложения и их перевод в HTTP-ответы.

## HTTP-контракты

Схемы запросов и ответов находятся в `packages/contracts/src/<feature>/`
и экспортируются из `src/index.ts`. Типы выводятся через `z.infer`.
Пакет не содержит Nest-декораторов, Prisma-моделей и React-кода.
Модели хранения остаются в API; даты в HTTP передаются строками.

Nest DTO наследует `createZodDto` общей схемы без повторения полей.
В health `ZodSerializerInterceptor` проверяет ответ по `@ZodSerializerDto`,
а Swagger использует тот же DTO. Глобальной валидации входящих DTO пока нет;
текущий эндпоинт не принимает тело запроса.

При добавлении эндпоинта согласуются схема, метод, путь и статусы ответа.
