# Синхронизация Excalidraw без Yjs

> Черновик: предложенный протокол не реализован. Результаты проверок относятся к текущему PoC.

Исследование от 23 ноября 2026 для выбора редактора CollabBoard. В PoC независимые правки могут пропадать, локальный Undo может перезаписать чужую правку того же поля, а перезагрузка после обрыва теряет несохранённые изменения. Эти ограничения затрагивают [требования к надёжности CollabBoard](../product.md#требования-к-надёжности).

## Как проводились проверки

Ветка `research/excalidraw-poc`, ревизия `9d6417ac`, Node.js 26.13.1, Excalidraw 0.18.1. Временный Playwright-скрипт запустил две вкладки Chromium с реальным Next.js-редактором и отдельным NestJS Gateway. Стикеры созданы штатной кнопкой, изменения выполнены мышью и клавиатурой, Undo/Redo — кнопками редактора. Состояние прочитано через `getSceneElementsIncludingDeleted()`. Текущее состояние Gateway проверено третьим подключением по его первому сообщению. [Запуск PoC](excalidraw-poc.md#запустить-и-проверить).

Для каждой гонки A и B начинали с одной сцены. Скрипт удерживал исходящие сообщения обеих вкладок до завершения их правок и выпускал последние снимки, по одному на клиента. Проверены оба порядка доставки. Для Undo/Redo задержки убраны, следующее действие начиналось после доставки предыдущего. Для offline закрыт только WebSocket A, Gateway и вкладка B продолжали работать. Сравнивались координаты стикеров, текст первой заметки, признаки удаления и версии её прямоугольника и подписи.

PASS означает, что сценарий выполнил указанное ожидание. FAIL означает воспроизведённое нарушение этого ожидания. Проверки охватывают выбранные порядки доставки и два стикера в Chromium.

## Конкурентные изменения

| Сценарий и ожидание | Итог на сервере | Состояние вкладок после доставки |
| --- | --- | --- |
| **FAIL** — A перемещает X, B перемещает Y. Оба перемещения должны сохраниться | При A → B сохранён только Y. При B → A сохранён только X | A показывает только перемещение Y, B — только X |
| **FAIL** — A и B перемещают X. Все должны увидеть одну выбранную позицию | При A → B сохранена позиция B. При B → A — позиция A | A показывает позицию B, B — позицию A |
| **FAIL** — A удаляет X, B меняет его текст. Удаление и конфликт должны быть обработаны одинаково у всех | При A → B X снова виден с новым текстом. При B → A X удалён, новый текст потерян | A видит X с текстом B. B видит удаление |
| **FAIL** — A меняет текст X, B перемещает X. Текст и перемещение должны сохраниться | При A → B сохранено перемещение со старым текстом. При B → A сохранён новый текст со старой позицией | A показывает перемещение со старым текстом. B показывает новый текст на старом месте |

Gateway заменяет весь снимок в памяти и рассылает его всем, кроме отправителя. При скрещивании снимков каждый отправитель принимает снимок другого, а сервер хранит последний принятый. Клиент применяет входящую сцену целиком и подавляет её повторную отправку. Поэтому даже после доставки обоих сообщений общего состояния нет. В проверках дополнительная пауза в 300 мс не изменила результат. [Gateway](../../apps/api/src/modules/research-excalidraw/excalidraw.gateway.ts), [клиент PoC](../../apps/web/src/_pages/research-excalidraw/ui/ExcalidrawEditor.tsx).

Удаление оставляет `isDeleted: true` у прямоугольника и подписи, но сцена другого клиента может заменить оба элемента живыми копиями. У стикера текст и прямоугольник имеют разные ID, однако перемещение обновляет и геометрию подписи. Поэтому отправка целого элемента по ID сама по себе не гарантирует одновременное сохранение текста и координат стикера.

## Undo и Redo

| Действия после исходной позиции X = (320, 349) | Undo пользователя A | Следующий Redo пользователя A |
| --- | --- | --- |
| **PASS** — A перемещает X в (420, 349) | X возвращается в (320, 349) | X снова в (420, 349) |
| **PASS** — A перемещает X по горизонтали, B перемещает Y | X возвращается, Y остаётся на позиции B | Восстанавливается перемещение X, позиция Y сохраняется |
| **FAIL** — A перемещает X до x = 420, B перемещает X дальше до x = 470 | X возвращается к x = 320. Чужое перемещение исчезает | X возвращается к x = 470, то есть к позиции непосредственно перед Undo |
| **PASS** — A меняет x, B меняет только y у X | X переходит из (420, 429) в (320, 429). Координата B сохраняется | X снова в (420, 429) |
| **PASS** — A перемещает X, B меняет подпись X | Позиция A отменяется, новый текст B остаётся | Позиция A восстанавливается, текст B остаётся |

После каждой команды вкладки и сервер совпали по измеренным полям. Версии затронутых элементов менялись, поэтому результат Undo/Redo уходил по обычному `onChange`. После первого входящего перемещения A кнопка Undo у B оставалась неактивной.

В PoC входящие сцены применяются через `updateScene({ elements, captureUpdate: CaptureUpdateAction.NEVER })`. В релизе 0.18.1 `NEVER` обновляет снимок Store без добавления записи в локальную историю. `IMMEDIATELY` сразу фиксирует изменение для Undo. `EVENTUALLY` оставляет изменение для следующей фиксации и поэтому не годится для применения чужой сцены. `updateScene({ elements })` заменяет массив сцены, так что принимающий клиент должен сначала собрать полный массив из своих данных и полученных изменений. [Store](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/store.ts), [исходник App](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/components/App.tsx), [API редактора](https://plus.excalidraw.com/docs/sdk/excalidraw/api/props/excalidraw-api).

История применяет обратную дельту к текущей сцене. Она сохраняет многие чужие изменения вне затронутых полей, но при совпадении полей может записать старое значение поверх чужого. При переносе записи в стек Redo редактор учитывает значения перед Undo, что объясняет возврат к позиции B. `NEVER` управляет захватом истории и не определяет владельца поля. Публичный `api.history` в типах установленного пакета предоставляет `clear()`. Управление семантикой совместного Undo остаётся задачей интеграции. [История](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/history.ts), [дельты](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/change.ts), [команды Undo/Redo](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/actions/actionHistory.tsx).

## Обрыв соединения

| Ожидание | Результат |
| --- | --- |
| **PASS** — A может продолжать редактирование локально, B остаётся онлайн | A переместил X, B переместил Y. A видел только свою правку, B и сервер — только правку B |
| **FAIL** — открытая вкладка A автоматически возобновляет связь | После закрытия сокета новых подключений не было в течение 1,2 с. В коде после `onclose` нет повторного открытия. По-прежнему можно редактировать локально |
| **PASS** — после нового подключения A получает актуальное состояние комнаты | После перезагрузки A получил перемещение Y, состояние обеих вкладок совпало с сервером |
| **FAIL** — несохранённая offline-правка A переживает переподключение | X вернулся на исходную позицию. A не отправил ни одного снимка после отключения, очереди для повтора нет |

Ручное сохранение в браузере оставляет локальную копию. При её восстановлении по кнопке в подключённой вкладке PoC отправляет восстановленный снимок целиком. По коду это может затереть изменения B и потому не заменяет процедуру восстановления соединения. Состояние комнаты живёт в памяти процесса. [Клиент PoC](../../apps/web/src/_pages/research-excalidraw/ui/ExcalidrawEditor.tsx), [Gateway](../../apps/api/src/modules/research-excalidraw/excalidraw.gateway.ts).

## Механизмы Excalidraw и официального приложения

| Где | Что доступно |
| --- | --- |
| Пакет редактора 0.18.1 | `onChange`, чтение сцены вместе с удалёнными элементами, `updateScene`, локальная история, отдельные API файлов. У элементов есть `id`, `version`, `versionNonce`, `isDeleted` и `index` для порядка. Редактор обновляет версии при мутациях, включая проверенные Undo/Redo |
| Экспортируемый `reconcileElements` | Объединяет по ID, сохраняет локальные элементы, которых нет во входящем массиве, и упорядочивает результат по `index`. Для одного ID предпочитает большую `version`, при равенстве — меньший `versionNonce`. На точном равенстве берёт входящий элемент. Локальное редактирование текста, изменение размера и создание также могут дать приоритет локальной копии |
| Официальный веб-клиент | `Portal` отправляет новые элементы и элементы с выросшей версией относительно последней отправки. При входе и при отложенной полной синхронизации после изменений он отправляет полный набор подходящих элементов. При получении `Collab` восстанавливает данные, согласует элементы и применяет их с `NEVER`. Удалённые элементы отправляются ограниченное время |
| Официальная серверная часть | `excalidraw-room` пересылает зашифрованные сообщения Socket.IO. Клиентское приложение хранит зашифрованные снимки в Firestore, согласуя ранее сохранённую сцену внутри транзакции. Файлы хранятся отдельно в Firebase Storage |

Сигнатуры API и экспорт `reconcileElements` сверены с типами установленного пакета. Источники для версии 0.18.1 и код отдельного сервиса ретрансляции. [Экспорты пакета](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/index.tsx), [reconcileElements](https://github.com/excalidraw/excalidraw/blob/v0.18.1/packages/excalidraw/data/reconcile.ts), [Portal](https://github.com/excalidraw/excalidraw/blob/v0.18.1/excalidraw-app/collab/Portal.tsx), [Collab](https://github.com/excalidraw/excalidraw/blob/v0.18.1/excalidraw-app/collab/Collab.tsx), [фильтр удалённых элементов](https://github.com/excalidraw/excalidraw/blob/v0.18.1/excalidraw-app/data/index.ts), [Firebase](https://github.com/excalidraw/excalidraw/blob/v0.18.1/excalidraw-app/data/firebase.ts), [excalidraw-room](https://github.com/excalidraw/excalidraw-room/blob/master/src/index.ts).

`reconcileElements` выбирает целый объект. При совпадении ID поля не объединяются, у `isDeleted` нет отдельного приоритета, а активное редактирование влияет на выбор. Поэтому для NestJS с авторитетным состоянием нужен собственный порядок подтверждения и применения операций. `version` и `versionNonce` редактора подходят для обнаружения изменений, но не заменяют серверную ревизию, подтверждение или историю авторства.

## Минимальный протокол для NestJS

1. **Операции по элементам.** Клиент диффит `onChange` по ID относительно своего предыдущего представления, включая удалённые элементы. Хранит копии или отпечатки, поскольку редактор может мутировать объекты. Отправляет изменившиеся элементы пакетом с `opId` и базовыми серверными ревизиями затронутых ID. Для стикера контейнер и подпись правятся атомарно. Промежуточные кадры drag можно объединять, сохраняя последнее изменение. Клиент собирает массив в порядке `index` и применяет подтверждённые события через `NEVER`. Сопоставление с подтверждённым состоянием и ожидающими операциями исключает эхо входящих изменений, в том числе при отложенном `onChange`.
2. **Авторитетный сервер.** NestJS проверяет право записи и структуру пакета, затем последовательно применяет операции по доске. PostgreSQL в одной транзакции сравнивает базовые ревизии элементов, обновляет их, выдаёт возрастающий `boardRevision` и фиксирует результат `opId`. После фиксации транзакции сервер отправляет канонические данные всем вкладкам, включая автора. Повтор `opId` возвращает прежний исход, конфликт устаревшей операции возвращает актуальные элементы и причину отказа. Правки разных ID проходят независимо. Для одновременной записи одного ID MVP сохраняет первую принятую операцию, а конфликтную правку оставляет клиенту для повторного применения или отказа.
3. **Удаление.** Явная операция удаления сохраняет tombstone по ID и применяется к связанным элементам атомарно. Если редактирование пришло первым, следующее удаление живого ID скрывает элемент. Если удаление пришло первым, позднее редактирование получает конфликт и не оживляет элемент. Возврат возможен через отдельную условную операцию восстановления. На старте проще сохранять tombstones. Для очистки позже нужен срок offline-поддержки и правило, по которому старый клиент переинициализируется и получает конфликты для просроченных операций.
4. **Undo/Redo с авторством.** Клиент ведёт историю пользовательских действий по подтверждённым операциям и формирует обратные команды по семантическим полям. Для каждого поля сервер сравнивает текущую запись с операцией, которую A хочет отменить. Если поле после A записал B, обратная команда это поле пропускает или сообщает конфликт. Для связанного набора полей и элементов сервер может отказать всей операции, чтобы не нарушить связи. Например, сохранение чужой подписи при Undo перемещения требует менять геометрию без записи текста. Redo проверяет результат собственного Undo таким же образом. В MVP можно начать с условного Undo целого атомарного действия по ревизиям затронутых ID. При чужом изменении того же элемента оно будет консервативно недоступно, пока нет учёта полей. Нужен отдельный прототип подключения обработчиков для кнопок и горячих клавиш Excalidraw, чтобы встроенный Undo не отправлял безусловную правку через `onChange`.
5. **Reconnect и offline.** Клиент хранит последний подтверждённый снимок, `boardRevision` и очередь операций в IndexedDB. После reconnect запрашивает изменения после своей ревизии или полный снимок, если журнал недоступен. Подписка и снимок должны идти от одной ревизии. События, пришедшие во время загрузки снимка, применяются после него в порядке ревизий. Неподтверждённые операции, в том числе при потере ACK, отправляет с прежними `opId` в исходном порядке. Повторная отправка учитывает зависимости между локальными операциями, например перемещение после локального создания. Нельзя просто подменить исходные ревизии актуальными, иначе потеряются чужие изменения. Независимые операции принимаются, конфликтные остаются локальными черновиками. При пропуске `boardRevision` клиент запрашивает актуальные данные повторно.
6. **Хранение.** PostgreSQL хранит текущие элементы по `(boardId, elementId)`, ревизию доски, tombstones, порядок и результаты операций для дедупликации. Для небольшого MVP можно отдавать полный канонический снимок при каждом reconnect. Журнал с ограниченным сроком хранения нужен, если потребуется догонять по ревизиям. Журнал доставки имеет отдельный жизненный цикл от продуктовой истории версий доски. Файлы хранятся по `fileId` отдельно от JSON элементов, курсоры и выделение передаются как временное состояние.

Описанная политика разрешает конфликты по ID без автоматического объединения двух изменений одного элемента. Если для MVP нужно одновременно сохранять текст и перемещение стикера, потребуется согласование семантических групп полей и пересчёт геометрии подписи. Работа с привязками стрелок и порядком слоёв потребует таких же явно определённых правил.

## Сложность и риски для MVP

Оценка относительная. Она основана на наблюдениях PoC и требованиях к предлагаемому протоколу.

| Задача | Сложность | Что определяет объём |
| --- | --- | --- |
| Передача изменений по ID, ревизии и tombstones | Средняя | Дифф, канонический ответ автору, атомарность связанных элементов, подавление эха |
| Снимок в PostgreSQL и reconnect по снимку | Средняя | Транзакция, идемпотентность, согласование снимка с подпиской, обработка пропусков |
| Совместный Undo/Redo | Высокая | Интеграция команд редактора, авторство и группировка полей, изменения во время жеста, работа после конфликта |
| Offline с сохранением правок | Высокая | Устойчивая очередь, зависимости операций, потерянные ACK, повтор после перезагрузки и UI конфликтов |
| Согласование полей и связанных объектов | Высокая | Подписи, стрелки, слои и поведение удалений при параллельном редактировании |

Даже при серверной сходимости пользователь может потерять действие в конфликте одного ID. Сохранение черновика и явный статус конфликта необходимы, чтобы потери не были тихими. Правки во время drag или набора текста, многопользовательские сценарии с 3+ клиентами, большие сцены, файлы, конкуренция разных экземпляров Gateway и reconnect при потерянном ACK в этом исследовании не проверялись. Развёртывание на нескольких экземплярах требует общей доставки событий и восстановления пропусков поверх общей БД. Требуемые продуктом права доступа действуют и при подписке, и при каждой записи.

## Рекомендация

Собственный универсальный sync-движок для MVP не оправдан, если с первого релиза нужны бесшовное offline-редактирование и Undo своих действий при любых чужих изменениях. Excalidraw даёт редактор, версии элементов и основу локальной истории. Сложные гарантии придётся проектировать и проверять команде.

Если Excalidraw важен как редактор и допустимы видимые конфликты, оправдан небольшой серверный протокол для онлайн-режима. Порог для продолжения — операции по ID, единое состояние после reconnect, отсутствие случайного восстановления удалённых объектов и условный Undo, который сохраняет чужие правки. До подтверждения этих свойств выбор Excalidraw как основного редактора стоит считать открытым.
