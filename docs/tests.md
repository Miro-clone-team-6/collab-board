# Как писать и выбирать тесты

Тест нужен, чтобы заметить конкретную поломку при изменении кода. Каждый тест
занимает время при чтении, запуске и сопровождении. Добавляем его, когда защита
от регрессии оправдывает эти затраты. Количество тестов и процент покрытия
сами по себе не являются целью. Если правка маленькая — тест может быть один или вообще отсутствовать, если проверять нечего.

## Какие уровни используем

**Основа — integration. Unit добавляем для самостоятельной логики,
e2e — для главных сквозных сценариев по мере их реализации.**
Обязательной пропорции между уровнями нет. Одна фича не обязана иметь все три.

| Уровень | Что проверяет | Когда выбирать |
| --- | --- | --- |
| Unit | Отдельное правило или алгоритм без приложения, сети и БД | Много значимых комбинаций входных данных; ошибка находится внутри вычисления |
| Integration | Совместную работу нескольких реальных частей: HTTP-обработку, модуль с БД, UI с обработчиками и состоянием | Риск на стыке частей; основной выбор для поведения приложения |
| E2E | Путь пользователя через браузер, Next.js, API и тестовую БД | Нужно убедиться, что весь путь работает после сборки и подключения приложений |

Только integration достаточно для старта, но это не запрет других уровней.
Математику холста удобнее проверять без браузера; integration с подменённым
HTTP не доказывает, что фронтенд и API действительно соединены.
Одинаковое сравнение ожидаемого и фактического значения может быть полезно
на любом уровне: важны происхождение результата и проверяемое правило.

## Как решить, нужен ли тест

Перед написанием сформулируй: **«Если сломается X, этот тест упадёт,
потому что проверяет Y»**. X — правдоподобная ошибка, Y — наблюдаемый результат.
Если вместо X получается только «код поменяется», уточни проверку или не добавляй её.

1. Определи последствия: потеря данных, чужой доступ, неработающий основной
   сценарий важнее второстепенной детали отображения.
2. Посмотри существующие тесты. Расширь подходящий сценарий, если новая проверка
   не защищает отдельное правило. Не заводи новый файл ради каждого метода.
3. Выбери самый узкий уровень, на котором проявляется реальная ошибка.
   Для ошибки SQL нужна настоящая БД; для преобразования координат она не нужна.
4. Выбери значимые случаи: основной результат, опасный отказ, границу правила.
   Не перебирай все значения, если они проходят один и тот же путь без нового риска.

Приоритет при изменениях:

- Исправляешь баг — добавь воспроизведение, которое падает до исправления
  и проходит после. Если автоматизация несоразмерно дорога, опиши причину
  и ручную проверку в PR.
- Меняешь права, сохранение, транзакции, обработку ошибок или контракт —
  проверь затронутые гарантии, включая опасные отказы.
- Добавляешь поведение — проверь его результат и те ошибки, которые меняют
  действия пользователя или состояние данных.
- Меняешь тексты, стили, тонкий реэкспорт или рефакторишь без смены поведения —
  отдельный тест обычно не нужен. Запусти существующие проверки.

Покрытие помогает найти непросмотренный код, но не заменяет выбор сценариев.
Не вводим общий порог и не дописываем тесты ради зелёных строк отчёта.

## Что проверять в CollabBoard

| Риск | Полезная проверка | Уровень |
| --- | --- | --- |
| В HTTP-ответ попали детали внутренней ошибки | Неожиданное исключение даёт публичный ответ без исходного сообщения и причины | Integration: реальный HTTP и фильтр |
| Неверно обработана недоступность БД в healthcheck | Ошибка зависимости приводит к HTTP 503 и состоянию `disconnected` | Integration: HTTP и настоящий сервис; отказ БД можно подставить |
| Наблюдатель изменяет доску прямым запросом | API отказывает, содержимое в БД остаётся прежним | Integration: авторизация, модуль, тестовая БД |
| Сохранение частично применилось при ошибке | После отказа нет частично записанных данных | Integration: настоящая транзакция и БД |
| Повторное событие создаёт дубликат | Повторная доставка оставляет один результат | Integration: обработчик и хранилище |
| Ошибка преобразования координат | При заданных масштабе и смещении получается ожидаемая точка, включая границы | Unit |
| После ошибки формы пользователь теряет ввод | Ошибка видна, введённые данные сохранены, повторная отправка возможна | Integration: UI и управляемый HTTP-ответ |
| Сборка приложений нарушила основной путь | Создать доску через UI, открыть её после перезагрузки и увидеть сохранённое содержимое | E2E |
| Изменения не доходят до другого участника | Два независимых браузерных контекста видят согласованное состояние | E2E; подробные случаи конфликтов — ниже, на integration/unit |

Не переносим все комбинации в браузер. Например, права подробно проверяются
на API, а e2e подтверждает, что интерфейс и сервер вместе поддерживают выбранный
путь. Повтор на другом уровне оправдан, если ловит другую поломку.

## Как писать полезный тест

- Названия и описания тестов в коде (`describe`, `test`, `it`) пишем на английском.
  Название описывает условие и результат: `viewer cannot modify a board`,
  `repeated event does not create a second element`. `works` или `test service` недостаточно.
- Структура: подготовить данные → выполнить действие → проверить результат.
  У теста одно понятное поведение; несколько связанных assertions допустимы.
- Вызывай код приложения через подходящую границу и проверяй результат:
  ответ, сохранённое состояние, видимую ошибку. В UI ищи элементы по роли,
  подписи или устойчивому идентификатору, когда доступного имени недостаточно.
- Ожидаемое значение выводи из требования. Не вычисляй его той же функцией,
  которую проверяешь, и не копируй её алгоритм в тест.
- Для запрета или ошибки проверяй и отсутствие нежелательного эффекта,
  если это часть гарантии. Один HTTP 403 не доказывает, что запись не изменилась.
- Используй минимальные осмысленные фикстуры. Разным условиям — отдельные
  сценарии или небольшая таблица случаев; не нужен гигантский объект «на всё».
- Для изменяемых полей вроде timestamp проверяй требуемый формат или диапазон,
  либо управляй временем, если точное значение относится к правилу.

**Не добавляем:**

- `expect("a").toBe("a")`, сравнение фикстуры с самой собой или тест,
  в котором весь результат вернул мок, а код приложения не участвовал;
- тест на каждый геттер, тип, реэкспорт, константу маршрута или наличие компонента
  без отдельной гарантии, которую важно сохранить;
- проверки внутреннего порядка вызовов, приватных методов и числа обращений
  к репозиторию, если это не самостоятельное требование;
- повторную проверку возможностей Zod, Prisma или React. Проверяем собственные
  ограничения схем и то, что приложение применяет их на нужной границе;
- большие snapshots DOM/JSON «на всякий случай». Проверяем значимые поля;
  снимок допустим, если само представление — предмет проверки и diff обозрим.

Тест обязан падать при нарушении обещания. При сомнении временно убери
проверку прав, измени результат вычисления или отключи сохранение и запусти тест.
Если он всё ещё зелёный, он не защищает заявленное поведение.

## Реальные зависимости и моки

Мок подменяет границу, которую этот тест не проверяет. Он не должен подменять
само проверяемое поведение.

- API + БД: для запросов, ограничений, транзакций и сохранения используем
  отдельную тестовую PostgreSQL с миграциями проекта. Мок Prisma эти гарантии
  не проверяет. Не подключаем тесты к рабочей или личной dev-базе.
- Внешние сервисы: подменяем на границе HTTP/SDK, задаём успешный ответ,
  значимый отказ или таймаут. Не делаем обычный прогон зависимым от живого провайдера.
- UI integration: допустимо подменить HTTP, оставив настоящими компонент,
  обработчики и нужные провайдеры. Ответы соответствуют общим контрактам;
  намеренно неверный ответ — отдельный сценарий.
- E2E: собственные web и API работают вместе с тестовой БД.
  Подмена собственного API превращает проверку в браузерный UI integration;
  она не подтверждает сквозной путь.

Каждый тест создаёт нужные данные сам и не зависит от порядка запуска.
Для параллельных тестов разделяем данные или схемы/базы и очищаем только
свои записи. После теста закрываем приложение, соединения и подписки,
восстанавливаем изменённые глобальные значения и моки.
Не используем случайные данные без воспроизводимого seed.
Вместо фиксированных задержек ждём конкретного состояния с ограниченным таймаутом.
Повторный прогон не считается исправлением нестабильного теста.

## Быстрая проверка перед запуском окружения

Из корня репозитория:

```bash
pnpm test
```

Команда запускает все подключённые автономные тесты без `pnpm dev`, Docker
и внешних сервисов. Показывает названия сценариев, успешные и упавшие проверки,
длительность и итог. При падении возвращает ненулевой код, но продолжает
независимые наборы, чтобы получить результаты за один запуск.
Тесты выполняются заново; необходимые сборки могут браться из кэша.

Новые автономные unit/integration-тесты подключаем через скрипт `test` своего
workspace: один прогон без watch-режима, с необходимой подготовкой и освобождением
ресурсов. Они автоматически попадут в общую команду. Тесты с настоящей БД и e2e
подключаем отдельными командами с явно описанной подготовкой окружения;
быстрый прогон их не заменяет.

## Проверка на ревью и при работе с ИИ

Человек проверяет:

- Понятно ли из имени и assertions, какую поломку обнаруживает тест?
- Участвует ли настоящее проверяемое поведение, а не только моки?
- Есть ли важная непроверенная граница: отказ, чужие данные, частичная запись?
- Переживёт ли тест рефакторинг с сохранением поведения?
- Добавляет ли он гарантию, которой нет в существующих сценариях?

ИИ следует тем же правилам: сначала назови риск и посмотри существующие тесты,
затем добавь минимальный набор сценариев. Не генерируй тест на каждый метод,
все комбинации входов или формальное покрытие строк. Не ослабляй assertions
и не обновляй snapshots без проверки изменившегося требования.
Устаревшие и дублирующие тесты можно удалить, если нужная гарантия сохранена.
