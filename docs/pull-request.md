# Ветки, коммиты и Pull Request

## Ветки и PR

Работа ведётся в отдельной ветке. В PR указывается целевая ветка;
если изменения зависят от другого PR, его ветка используется как база до слияния.
После слияния зависимого PR база меняется на общую целевую ветку.
В diff должны оставаться только изменения задачи.

Заголовок PR — в формате коммита. Описание содержит результат изменения,
способ проверки и известные ограничения. Связанная задача и зависимые PR
указываются ссылками. Ссылка на другой PR сама по себе не блокирует слияние.

## Коммиты

```text
<type>(<scope>): <message>
```

Типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `style`, `chore`, `ci`.
Scope обязателен: например, `api`, `web`, `contracts`, `repo`, `infra`.
Сообщение — на английском, в повелительном наклонении, без точки в конце:
`fix(api): return 503 when database is unavailable`.
Тело коммита добавляется, если заголовка недостаточно для описания изменения.

Husky запускает lint-staged перед коммитом и commitlint для сообщения.
Commitlint проверяет тип и наличие scope; язык и смысл сообщения проверяются на ревью.

## Перед ревью

Из корня репозитория:

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

При изменении поведения API проверить затронутый сценарий.
Команды работы с БД — в [разделе БД](backend/db-and-migrations.md#миграции).
Изменение структуры БД сопровождается SQL-миграцией; изменение только генератора
Prisma миграции не требует. Изменённое поведение отражается в документации.

Критерии ревью — в [review.md](review.md).

## Проверки CI и слияние

Workflow [CI](../.github/workflows/pr-checks.yml) запускается для каждого PR независимо
от целевой ветки и изменённых файлов, в том числе для правок документации.
Задание `PR checks` проверяет результат объединения с целевой веткой:
линтеры, типы, миграции, тесты и production-сборку. Новый коммит отменяет
устаревший запуск и запускает проверки заново.

CI создаёт временную PostgreSQL с пустой БД `collab_board_ci` и применяет
все закоммиченные миграции через `pnpm db:migrate:deploy`. База существует
только в рамках задания; рабочие окружения и секреты деплоя не используются.
Автономные тесты API подменяют зависимость от БД, поэтому шаг миграций
проверяет SQL отдельно от тестов.

Для локального воспроизведения выполнить команды из раздела «Перед ревью».
Для проверки миграций сначала подготовить отдельную пустую PostgreSQL,
передать её адрес в `DATABASE_URL` и выполнить:

```bash
pnpm db:migrate:deploy
```

Для слияния в `develop` и `main` требуются успешный `PR checks` и минимум одно
одобрение другого участника команды. Новые изменения в коде сбрасывают старое
одобрение, если администратор включил соответствующее правило защиты.

## Настроить защиту веток

Настройка требует административных прав в GitHub. Роли `MAINTAIN` недостаточно.
До включения ruleset GitHub не блокирует слияние по требованиям выше.

1. Открыть первый PR с workflow и дождаться появления статуса `PR checks`.
2. В Settings → Rules → Rulesets создать активный ruleset для `develop` и `main`.
3. Включить обязательный PR, минимум одно одобрение и сброс старых одобрений
   при новых изменениях в коде.
4. Сделать `PR checks` от GitHub Actions обязательным и включить требование
   актуальности ветки перед слиянием. Запретить force push и удаление веток.
   Оставить список обхода правил пустым.
5. Проверить на PR, что ошибка CI или отсутствие одобрения блокирует слияние.
   После переноса workflow в `main` через обычный PR проверить тот же статус там.

На первом PR с переименованным файлом workflow проверьте, что GitHub засчитал
`PR checks` в правилах защиты целевой ветки, если эта проверка обязательна.
