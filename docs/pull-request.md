# Ветки, коммиты и Pull Request

## Ветки и PR

Работа ведётся в отдельной ветке. В PR указывается целевая ветка;
если изменения зависят от другого PR, его ветка используется как база до слияния.
После слияния зависимого PR база меняется на общую целевую ветку.
В diff должны оставаться только изменения задачи.

Заголовок PR — в формате коммита. Описание содержит результат изменения,
способ проверки и известные ограничения. Связанная задача и зависимые PR
указываются ссылками. Ссылка на другой PR сама по себе не блокирует слияние.

## Коммиты

```text
<type>(<scope>): <message>
```

Типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `style`, `chore`, `ci`.
Scope обязателен: например, `api`, `web`, `contracts`, `repo`, `infra`.
Сообщение — на английском, в повелительном наклонении, без точки в конце:
`fix(api): return 503 when database is unavailable`.
Тело коммита добавляется, если заголовка недостаточно для описания изменения.

Husky запускает lint-staged перед коммитом и commitlint для сообщения.
Commitlint проверяет тип и наличие scope; язык и смысл сообщения проверяются на ревью.

## Перед ревью

Из корня репозитория:

```bash
pnpm typecheck
pnpm lint
pnpm build
```

При изменении поведения API: `pnpm --filter api test` и проверка затронутого
сценария. Команды работы с БД — в [разделе БД](backend/db-and-migrations.md#миграции-и-сиды).
Изменение структуры БД сопровождается SQL-миграцией; изменение только генератора
Prisma миграции не требует. Изменённое поведение отражается в документации.

Автоматических проверок GitHub Actions в репозитории пока нет.
Критерии ревью — в [review.md](review.md).
