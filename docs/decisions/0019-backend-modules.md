# 0003. Плоские модули backend

> Статус: ✅ Принято; текущий пример — модуль health.
> Дата: 2026-11-13.

## Контекст

Нужна структура, в которой видно обработку запроса и границы работы с БД,
без обязательного набора пустых слоёв и абстракций.

## Решение

Код группируется по функциональным модулям в `src/modules/<name>/`.
Файлы контроллера, DTO и сервиса лежат рядом. Подключение Prisma, конфигурация и обработка ошибок — общие компоненты
вне функциональных модулей.

Работу с данными бизнес-модуля скрывает репозиторий. Отдельные use case,
интерфейсы и вложенные слои добавляются по необходимости, а не при создании
каждого модуля. Технический healthcheck выполняет `SELECT 1` напрямую.

В дальнейшем бекенд будет проектироваться в соответствии с DDD-lite подходом и реализовывать типичные паттерны, отказываясь от тех, которые в данном контексте избыточны. Важно не наплодить лишних нечитаемых абстракций.

## От чего отказались

В идеале было бы сразу разделить структуру на явные слои на уровне репо: добавить `presentation/application/domain/infrastructure` внутри каждого
модуля. Но на текущем этапе они будут добавлять навигацию и шум в директориях без дополнительного поведения. При необходимости — будем добавлять разделение, если код становится трудночитаемым.

## Последствия

Новый модуль начинается с минимального набора файлов. Усложнение сценариев
может потребовать выделения use case или изменения структуры отдельного модуля.
Репозиториев и бизнес-сценариев в текущем каркасе ещё нет.
